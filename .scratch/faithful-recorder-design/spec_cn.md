# 忠实的 Claude Code 模型交换记录器

Status: ready-for-agent

## 问题陈述

通过 Claude Code CLI 或 VS Code 扩展使用 Claude Code，并通过 cc-switch 选择 DeepSeek V4 Flash 的用户，需要获得某一个 Claude Code 会话中模型流量的可信记录。面向用户的对话文本并不充分：它省略了请求元数据、系统内容、工具 schema、思考数据、流式事件、响应头，以及与模型交换的精确实体字节。

记录路径不得改变实际生效的模型配置、凭据、请求或响应含义，也不得改变流式行为。它必须在边界处保留两个来源发出的完整应用层 HTTP 模型交换（Model Exchange）：记录器（Recorder）收到的执行端（Harness）请求，以及记录器终止上游 TLS 后收到的模型（Model）响应。它还必须使代理创建的上游请求信封可供审计。

现有直连模型配置（Direct Model Profile）必须继续可以独立选择。记录必须使用一个单独的记录器配置（Recorder Profile）和一个独立 Linux 进程；cc-switch 只充当控制面的配置选择器。记录器必须通过稳定的 `x-claude-code-session-id` 请求头获取一个执行端会话（Harness Session），将锁保持到用户正常停止记录器，并以确定性的请求顺序记录该执行端会话中所有已准入的模型交换。

本仓库是一个绿地项目，没有需要保留的实现、包定义、构建系统或测试套件。因此，本规格必须足够精确地定义运行时、协议、产物、兼容性和验收契约，使后续实现 agent 无需重新讨论已经解决的十项设计决策，就能构建并验证记录器。

## 解决方案

为 Linux 构建一个小型、独立、零依赖的 Node.js 记录器。记录器监听可配置的 HTTP/1.1 socket，接收来自已选记录器配置的 Claude Code 流量，并与配置的 DeepSeek 兼容上游 base URL 建立第二条 HTTP/1.1 连接。它捕获来源侧的每一条应用层 HTTP 消息，同时在背压约束下，将请求和响应实体作为不透明字节流分流转发。

用户保留现有直连模型配置，并复制完整、实际生效的直连模型配置来创建一个单独的记录器配置，只把 `ANTHROPIC_BASE_URL` 改为记录器的回环 URL。用户启动记录器时提供真实上游 base URL 和输出根目录。凭据不单独配置：记录器把从执行端收到的认证字段作为普通端到端请求字段原样转发。

记录器启动时处于未锁定状态。第一个符合条件、恰好带有一个非空 `x-claude-code-session-id` 字段的 `POST /v1/messages` 请求，在请求头接收完成时获取锁，并被完整记录。之后，具有完全相同不透明会话标识的合格请求会记录到同一个会话目录。辅助流量不能获取锁，也不会成为被记录的模型交换。正常停止会关闭准入，让所有已准入模型交换排空至完成，完成产物最终化，然后退出。

记录产物是一个带版本、以会话命名的目录。它包含有序索引，以及每个模型交换各自的目录。每个交换把精确的请求和响应实体字节存入不透明文件；把来源 HTTP 元数据存为有序且保留重复项的字段对；并记录实际的上游请求元数据，包括所有允许的路由差异和逐跳差异。JSON 和 SSE 永远不会被解析、规范化、重新生成、脱敏、解压或重新压缩。

正确性由两个自动化层级证明。字节级回放测试通过记录器的真实监听 socket 和受控上游来测试组装完成的记录器，并把两个方向的转发流和落盘产物与已捕获的目标技术栈 fixture 对比。随后，实时验收在不打开 VS Code UI 的情况下驱动真实 Claude Code CLI 和扩展内置的 `claude-vscode` 入口。只有回放套件通过，并且两个实时入口都完成且产生有效记录，该功能才算验收通过。

## 实现决策

### 产品和拓扑边界

- 交付物是独立的 Linux **记录器（Recorder）**，其唯一数据面拓扑为 `Harness -> Recorder -> Model`。
- **Harness（执行端）**、**Model（模型）**、**Model Exchange（模型交换）**、**Harness Session（执行端会话）**、**Recorder（记录器）**、**Direct Model Profile（直连模型配置）** 和 **Recorder Profile（记录器配置）** 沿用项目领域词汇表中的定义。尤其是，模型交换是应用层请求/响应对，不是人类对话轮次，也不是一组 TCP chunk 或运行时 chunk。
- cc-switch 只充当控制面配置选择器。记录期间必须禁用其本地路由接管模式；其代理不得成为另一个数据面 hop。
- 现有直连模型配置继续可以单独选择。记录器永远不读取、编辑、重建、验证或切换任一配置。
- 用户复制完整、实际生效的直连模型配置来创建名称明显不同的记录器配置，并且只把 `env.ANTHROPIC_BASE_URL` 改为 `http://127.0.0.1:4318`；如果覆盖了默认监听 socket，则改为对应地址。
- 副本包含精确的凭据字段和值（`ANTHROPIC_AUTH_TOKEN` 或 `ANTHROPIC_API_KEY`）、fallback 和角色模型映射、子 agent 模型、其他所有实际生效的 Claude 设置、`meta.apiFormat` 和 `meta.apiKeyField`。复制正在工作的配置，不从 cc-switch preset 重新创建。
- “直连模型配置保持不变”是指记录器既不执行也不要求任何变更。cc-switch 普通模式的退出配置回填仍可能重写它存储的 provider row；记录器不保证 cc-switch 存储逐字节不变。
- 在没有更高优先级 Claude 或 VS Code 设置覆盖时，选择记录器配置会把两个受支持执行端入口都路由到记录器。选择直连模型配置无需查询记录器即可恢复直连数据路径。

### 运行时与启动契约

- 运行时使用 Node.js，要求 `engines >=22`；使用 ESM 模块、内置 `http` 和 `https`、内置文件系统能力，以及内置 `node:test` runner。运行时和测试均无第三方依赖，也没有编译/构建步骤。
- 可执行命令契约如下：

  ```text
  recorder \
    --upstream-base-url <absolute-base-url> \
    --output-root <directory> \
    [--listen 127.0.0.1:4318]
  ```

- `--upstream-base-url` 必填。它是绝对 `http` 或 `https` base URL，可以包含路径前缀，表示 Claude 兼容网关的基址，而不是完整的 `/v1/messages` 端点。
- `--output-root` 必填。它表示创建会话产物目录的父目录。
- `--listen` 可选，默认值为 `127.0.0.1:4318`。因此默认记录器配置的 base URL 是 `http://127.0.0.1:4318`。
- 运行时契约不包含配置文件、环境变量覆盖层、凭据选项、配置标识符、配置管理命令或 cc-switch 集成。
- 用户手动把直连模型配置中实际生效的 `ANTHROPIC_BASE_URL` 复制到 `--upstream-base-url`。记录器不会发现该值。
- 记录器不接收单独的上游凭据。它把来源发出的认证字段和值与其他端到端字段一起转发。

### 应用层 HTTP 接缝与忠实性边界

- 记录器是一个双侧流式应用层 HTTP 反向代理。它终止执行端的回环 HTTP/1.1 连接，并单独终止通往模型的 HTTP/1.1 连接；适用时，后者包含 TLS。
- 执行端入口是请求的权威来源观察点。捕获内容包括 HTTP 版本、方法、原始请求目标、每个有序请求 header 和 trailer 字段的原始名称与值，以及精确的请求实体字节序列。
- 上游 TLS 终止后的模型入口是响应的权威来源观察点。捕获内容包括 HTTP 版本、状态、原因短语、每个有序响应 header 和 trailer 字段的原始名称与值，以及精确的响应实体字节序列。
- Header 和 trailer 表示为二元素 `[name, value]` 数组的列表，不转换为 map。必须保留原始名称大小写、跨字段顺序、重复名称和重复值。
- 实体 body 是不透明的有序字节序列。记录器不得解析或重新生成 Messages JSON，不得解析或重新生成 SSE，不得规范化换行或分隔符，不得脱敏字段、注入内容、解码或重新编码文本、解压或重新压缩内容，也不得等到完整 body 后才转发。
- 凭据、系统提示、消息、工具输入和输出、思考内容、自定义字段及任何其他来源发出的应用数据都位于忠实性边界内，并且不经脱敏地记录。
- 精确的 HTTP header 行空白、传输成帧和 chunk-size 行、运行时交付边界、时间、TLS record、TCP 分段和数据包边界都位于忠实性边界之外。
- 允许运行时 chunk 拆分和合并。只要求拼接后的实体序列相等。
- 从执行端收到、写入产物并发送到上游的请求实体拼接字节必须逐字节完全相同。
- 从模型收到、写入产物并发送给执行端的响应实体拼接字节必须逐字节完全相同。
- 记录器把请求字段、响应字段、Messages body 字段和 SSE 事件类型都视为开放列表。兼容性不得依赖封闭的 header、JSON 或 SSE schema。

### 路由与转发契约

- 保留传入请求的方法和查询。上游请求目标通过把配置的上游 base path 与执行端请求目标的 path 连接起来形成，并保留执行端查询。
- 示例：上游基址 `https://api.deepseek.com/anthropic` 加执行端目标 `/v1/messages?beta=true`，得到上游目标 `/anthropic/v1/messages?beta=true`。
- 来源执行端目标保存在 `request.json` 中；第二个 hop 实际使用的连接后目标保存在 `upstream-request.json` 中。
- 请求实体和响应实体转发时不做语义转换。
- 端到端请求和响应字段，包括认证字段和未来未知字段，作为开放的有序列表转发。
- 唯一允许的信封变更是形成第二个 hop 所必需的封闭类别：为上游 authority 替换请求 `Host`；连接上游 base path；以及管理逐跳字段、连接状态、传输成帧和 TLS。
- 逐跳字段包括标准连接专用字段，以及由 `Connection` 指定的任意字段。来源元数据在这些字段被删除或改变之前捕获；实际的上游请求元数据记录路由信封决策后的结果。
- 不允许转换模型、凭据、Anthropic beta、Messages body、SSE 事件、内容编码或应用字段。
- token 计数、预热、发现、未知路径等辅助请求，或没有可用会话字段的请求，不能获取执行端会话，也不会创建模型交换产物条目。它们的存在不得与准入顺序混淆。
- 获取锁后，携带另一个会话身份的竞争性合格请求如何处理，刻意不在本规格范围内；操作契约要求一次运行中不出现并发的其他执行端会话。

### 执行端会话获取与生命周期

- 启动进程会创建一个处于未锁定状态并开始监听的记录器。
- 请求只有同时满足以下全部条件时，才有资格获取或匹配锁：

  1. 请求头接收完成。
  2. 方法为 `POST`。
  3. 请求 path 恰好是 `/v1/messages`；保留查询，但本项 path 检查忽略查询。
  4. 原始字段中恰好有一个名称按大小写不敏感匹配 `x-claude-code-session-id` 的字段。
  5. 从该唯一字段值两侧移除可选空白后，得到非空身份。

- 第一个合格请求在请求头完成时同步获取锁。此时分配交换编号并写入索引准入，早于实体或响应完成。
- 除 HTTP 边界要求的处理外，该值保持不透明。按大小写敏感方式精确比较；不把它解析为 UUID，不转小写、不做大小写折叠、不验证结构，也不从 body 派生。
- 获取锁的请求作为第一个模型交换纳入。只要进程仍然开放，后续每个具有完全相同会话身份的合格请求都会准入同一个产物。
- 交换顺序是请求头准入顺序，不是响应完成顺序、所有网络事件的挂钟顺序或 SSE 事件顺序。
- 锁永远不会释放、轮换，也不会持久化供另一个进程复用。一次进程运行最多生成一个执行端会话产物。
- 用户正常停止会把记录器从接受状态切换到排空状态：不得再准入新模型交换；每个已准入模型交换可以完成网络转发和产物写入；所有交换完成最终化后进程退出。
- 正常停止不会删除之前完成的条目，也不会创建额外完成标记、发布事务或持久锁文件。
- 如果正常停止前从未获取任何执行端会话，则不生成会话内容。
- 强制终止、崩溃、畸形输入、对端停滞、上游/网络故障、磁盘故障，以及从部分产物恢复，都不在范围内。

### 可逆会话组件

- 每当在文件名组件中使用会话身份时，都添加 `session-` 前缀，并按以下规则进行可逆编码：

  1. 把不透明身份编码为 UTF-8 字节。
  2. ASCII `A-Z`、`a-z`、`0-9`、`.`、`_` 和 `-` 保持不变。
  3. 其他每个字节都以大写 `%HH` 形式进行百分号编码。

- UUID 形状的身份仍然可读，例如 `session-a11f5b03-c280-4dc6-8c52-f0967d48948e`。
- 百分号编码仅用于文件名表示。身份比较使用移除两侧可选空白后的不透明 header 值。

### 产物契约

- 产物 schema 版本为 `1`。
- 具体形状来自已经审核的无损记录产物原型：

  ```text
  session-<reversibly-encoded-session_id>/
  ├── index.json
  └── exchange-000001/
      ├── request.json
      ├── request.body
      ├── upstream-request.json
      ├── response.json
      └── response.body
  ```

- 交换目录使用单调递增、零填充的准入编号，从 `exchange-000001` 开始。
- `index.json` 包含：

  - `artifact_version`：整数 `1`；
  - `session_id`：移除两侧可选空白后的精确不透明身份；
  - `exchanges`：按准入顺序排列的交换目录名。

- `request.json` 表示应用层执行端请求，包含：

  - `http_version`；
  - `method`；
  - `target`，保留原始执行端请求目标；
  - 有序且保留重复项的 `headers` 对；
  - 有序且保留重复项的 `trailers` 对；
  - `entity_file: "request.body"`。

- `response.json` 表示应用层模型响应，包含：

  - `http_version`；
  - 数值型 `status`；
  - `reason`；
  - 有序且保留重复项的 `headers` 对；
  - 有序且保留重复项的 `trailers` 对；
  - `entity_file: "response.body"`。

- `upstream-request.json` 表示实际向模型发出的应用层请求，包含：

  - 实际上游 HTTP 版本；
  - 方法；
  - 连接后的上游目标；
  - 路由和逐跳处理后的有序 header；
  - 实际转发到上游的有序 trailer；
  - `entity_file: "request.body"`。

- `request.body` 始终存在，并且只包含精确的来源请求实体字节。`response.body` 始终存在，并且只包含精确的来源响应实体字节。即使实体长度为零，两个文件也存在。
- 上游请求元数据引用 `request.body`，不写第二份 body 副本。
- 交换目录是配对边界。绝不能配对来自不同交换编号的元数据或 body 文件。
- 请求头准入时分配索引条目。来源 trailer 元数据只有在对应来源实体结束后才最终确定；交换生命周期早期持久化的元数据，必须在正常排空的交换完成之前以完整 trailer 列表最终化。
- 产物不保存原始传输成帧、交付 chunk 日志、时间、TCP/TLS 数据、面向用户的对话文本、派生 JSON、派生 SSE 索引、脱敏视图或完成标记。

### 流式与连接行为

- 两个方向都使用读取时分流（tee-on-read）。来源字节到达时，无需等待完整实体，即将其同时交给下一个网络 hop 和对应 body 文件。
- 分流遵守最慢 sink 的背压。实现可以暂停来源读取，直到两个目标都能继续；不得通过在内存中累积无界完整 body 来处理背压。
- 在模型响应实体完成之前，必须把最初的响应字节转发给执行端。
- 两个 hop 都使用 HTTP/1.1。回环服务器对非 HTTP/1.1 请求返回 `505`。上游 `http`/`https` 客户端不得协商 HTTP/2。
- 两侧连接都使用 keep-alive。上游请求共享一个 socket 池大小合理且有界的 Agent，使连续模型交换可以复用连接。
- 禁用会截断空闲连接的服务器请求超时和 header 超时，以支持有效的长时间 SSE 流。
- 上游 HTTPS 使用平台系统 CA 验证，不绕过验证，也不使用自定义信任行为。
- 请求和响应 trailer 在目标流结束前，通过相应 HTTP/1.1 trailer 机制转发；来源有序 trailer 对保留在元数据中。
- 基于触发事件的持久化遵循交换生命周期：准入建立目录、请求元数据、body sink 和索引条目；模型响应头建立响应元数据和实际上游信封元数据；实体完成后最终化 body 与 trailer。正常停止排空会等待所有已准入交换完成最终化。

### 逻辑模块边界

- 启动契约模块只解析已决定的三个 CLI 选项，并生成经过验证的运行时值。
- 服务器生命周期模块负责回环 HTTP/1.1 监听器、未锁定/已锁定/排空状态、准入、正常停止和上游 Agent 生命周期。
- 模型交换模块负责一个配对的双 hop 请求/响应流、来源侧观察、允许的信封变更、trailer、分流和背压。
- 产物模块负责可逆会话命名、带 schema 版本的元数据、body sink、交换编号、索引顺序和最终化。
- 组装入口负责连接这些职责并启动进程。
- 这些只是逻辑职责边界，不表示允许在模块之间规范化消息数据。原始有序字段对和不透明字节流在内部调用之间保持完整。
- 已接受 ADR 中关于 Node.js、零依赖、原生 HTTP 技术栈和 tee-on-read 流式处理的要求具有约束力。排除框架型反向代理和语义协议中间件。

### 兼容性契约

- 兼容性只有两个层级：Verified 表内版本和其他所有版本。不声明最低版本、版本范围、推断出的版本家族或未来版本。
- 以下技术栈于 2026-08-21 在 Linux 上完成测量：

  | 组件 | 已验证值 |
  | --- | --- |
  | Claude Code CLI 入口 | `2.1.238`（`sdk-cli`） |
  | Claude Code VS Code 扩展入口 | `2.1.238`（`claude-vscode`） |
  | VS Code host | `1.116.0` |
  | cc-switch | `3.15.0` |
  | DeepSeek 端点 | `https://api.deepseek.com/anthropic` |
  | 请求中观察到的模型 | `deepseek-v4-flash` |

- 记录器不包含客户端版本或 cc-switch 版本解析、allowlist、警告、功能 gate 或拒绝逻辑。
- 准入仍然只依据请求契约和会话字段。原样记录的 `User-Agent` 是被动来源信息，日后可以检查；`x-stainless-*` 字段不是兼容性信号。
- 目标技术栈 fixture 证明两个入口都发出了 HTTP/1.1 `POST /v1/messages?beta=true`，携带彼此不同但各自稳定的会话字段，并在所选接缝处收到增量交付的 DeepSeek SSE，且上游响应与 relay 响应 hash 逐字节一致。
- VS Code 证据覆盖官方扩展内置的模型客户端可执行文件及其 `claude-vscode` 启动环境，不覆盖 VS Code webview 或 extension-host UI IPC。

### 用户操作顺序

1. 保留现有直连模型配置。
2. 把它完整、实际生效的 provider 配置复制到名称明显不同的记录器配置，并且只把 `ANTHROPIC_BASE_URL` 改为记录器监听基址。
3. 确认 cc-switch 本地路由接管已禁用。
4. 使用直连路由的上游 base URL 和选定的输出根目录启动记录器。
5. 选择记录器配置。
6. 启动或恢复准备捕获的唯一执行端会话，并确保没有其他执行端会话使用同一个记录器进程。
7. 在记录器保持打开时，正常使用任一受支持执行端入口。
8. 正常停止记录器，并允许已准入模型交换排空。
9. 需要直连路由时，选择直连模型配置。

## 测试决策

### 测试理念与接缝

- 测试断言外部可观察行为，而不是内部调用顺序或实现细节。只要重构保留 HTTP 行为、产物字节、顺序和生命周期，就不应要求重写测试。
- 主要自动化接缝是可行范围内的最高层：通过真实监听 socket、受控 mock 模型端点、进程生命周期和临时输出根目录观察组装完成的记录器。执行端侧 driver 提供请求并读取响应。这一个接缝共同覆盖准入、路由、转发、流式、关闭和持久化。
- 只有当内部模块表达稳定公共契约时，才可以添加少量聚焦测试；内部 mock 不能代替组装后记录器测试。可逆会话命名和启动验证在可行时应优先通过进程/输出行为断言。
- 第二个接缝是与已安装执行端和模型技术栈的实时兼容性。它证明入口集成和流式完成，不证明字节真值。
- 仓库中没有现有测试套件可仿照。先例包括目标技术栈诊断捕获、其 manifest 和字节 fixture，以及已经审核的无损产物原型。实现应把这些资产转化为可重复的 `node:test` 场景。

### 第 1 层：字节级 fixture 回放

- 使用 `node --test` 运行，不依赖外部服务或凭据。
- 使用两个已捕获入口：CLI `sdk-cli` 和 VS Code 扩展 `claude-vscode`。
- 执行端侧 driver 通过记录器的真实监听 socket 发送每个已捕获请求。来源 fixture 中经过密钥脱敏的控制/header 值由确定性的合成测试值替代；已捕获 body 字节和非秘密来源字段顺序仍是权威真值。
- Mock 模型接收转发的请求，并返回已捕获状态、有序响应字段、trailer 和精确响应实体。它故意以缓慢的 chunk 发送响应实体，使测试能观察流式行为。
- 回放前使用 manifest 中的 SHA-256 值验证 fixture 完整性。
- 请求忠实性断言证明以下三个序列都与回放真值相同：

  1. 执行端侧 driver 提供的实体字节；
  2. mock 模型收到的拼接实体字节；
  3. `request.body` 中的字节。

- 响应忠实性断言证明以下三个序列都与回放真值相同：

  1. mock 模型发出的实体字节；
  2. 执行端侧 driver 收到的拼接实体字节；
  3. `response.body` 中的字节。

- Mock 模型还断言实际转发的请求方法、连接后的目标、端到端 header 和 trailer。执行端侧 driver 断言实际 relay 的响应状态、原因短语、端到端 header 和 trailer。两侧只允许规定的路由差异和逐跳差异。
- 元数据断言证明 `request.json` 和 `response.json` 保留来源起始行字段，以及有序且保留重复项的 header 和 trailer。即使实时 fixture 的 trailer 列表为空，测试也必须包含重复字段和 trailer。
- 上游审计断言证明 `upstream-request.json` 报告连接后的 base-path 目标、上游 `Host`、实际 HTTP 版本、已转发端到端字段、已转发 trailer，以及完整的逐跳/路由差异集合。它必须引用同一个 `request.body`。
- 产物断言证明精确会话组件编码、`artifact_version: 1`、精确 `session_id`、单调编号的交换目录、必要文件存在，以及索引顺序。
- 准入顺序测试让同一会话中的多个模型交换重叠，并故意让响应乱序完成。`index.json` 必须保留请求头准入顺序。
- 合格性测试在第一个 Messages 请求前发送辅助流量，包括没有可用会话字段的 count-tokens 类请求。它既不能获取锁，也不能创建交换目录。
- 会话字段测试覆盖字段名大小写、两侧可选空白、空值、重复原始字段、精确的大小写敏感身份比较，以及需要 UTF-8 百分号编码的不透明非 UUID 身份。
- 流式测试在发出初始前缀后保持 mock 响应打开。执行端必须在响应实体完成前收到该前缀。不做挂钟延迟阈值断言。
- 背压测试使用故意缓慢的目标，并在不假设来源 chunk 边界得到保留的前提下验证完整相等性。
- 合成 keep-alive 测试通过一条执行端连接连续发送多个交换，同时让 mock 模型观察上游连接复用。它覆盖已捕获 fixture 中缺少的行为；fixture 的上游响应使用了 `Connection: close`。
- 合成零长度实体测试证明所需 body 文件存在且长度为零。
- 通过发送非 HTTP/1.1 请求并断言返回 `505` 来测试 HTTP 版本行为，并且不得准入模型交换。
- 正常停止测试先启动一个交换，在其响应尚未完成时发起受支持的正常停止，再完成响应。执行端收到完整响应，产物完成最终化，后续请求不被准入，之前保存的交换仍然存在。
- 无获取锁正常停止测试证明不会生成会话产物。
- 交付边界、时间、原始 chunk 大小、TLS record 和 TCP 分段永远不是相等性断言。fixture 的交付 chunk 记录只保留为诊断文档。
- 只有每项字节、元数据、顺序、合格性、流式、keep-alive、空实体、HTTP 版本和正常停止断言都成功，第 1 层才通过。

### 第 2 层：实时目标技术栈验收

- 第 2 层只在具有 Verified 技术栈、有效 DeepSeek 访问、已选择 cc-switch 记录器配置，并可访问已安装客户端入口本地路径的已配置 Linux 主机上运行。驱动过程自动且非交互。
- 每个场景都从新的记录器进程和新的执行端会话开始，使预期会话成为观察到的第一个合格身份。
- CLI 场景：非交互运行 `claude -p "<prompt>"`，由记录器配置把进程路由到记录器监听基址。
- VS Code 入口场景：运行已安装官方扩展中逐字节相同的原生可执行文件，并设置 `CLAUDE_CODE_ENTRYPOINT=claude-vscode`、`MCP_CONNECTION_NONBLOCKING=true` 和 `CLAUDE_CODE_ENABLE_TASKS=0`。
- 不需要打开 VS Code 窗口，也不需要自动化 webview 或 extension-host UI。
- 每个场景都断言客户端在收到流式响应后正常退出，并且输出根目录包含结构正确的会话目录、有序索引，以及每个已准入交换的完整文件。
- 实时产物保留为未来 fixture 候选。由于不存在第三个实时字节真值来源，它们不能独立证明字节相等。
- 一次成功运行不会自动扩展 Verified 表。兼容性声明只能通过有审核证据支持的显式规格更新来改变。
- 整体验收要求第 1 层全部通过，然后两个入口都成功完成实时记录。

## 范围之外

- 安全和隐私设计，包括脱敏、秘密清理、访问控制、加密、产物权限、安全删除和保留策略。
- 故障和恢复行为，包括进程崩溃、强制终止、畸形流量、连接停滞、DNS/TLS/网络错误、上游不可用、磁盘耗尽、写入失败、产物冲突，以及修复中断的元数据或 body 文件。
- 第一次获取锁后，并发或其他会话身份的处理策略。用户操作契约会防止该情形。
- 锁轮换、自动会话轮换、单次运行捕获多个会话，或持久锁恢复。
- macOS 和 Windows 支持、打包或验收测试。
- 泛化到 Claude Code 以外的执行端，或配置的 DeepSeek V4 Flash 端点以外的模型。
- 对 Verified 表中未列版本的兼容性声明，包括较旧且没有该 header 的 Claude Code 版本和未来版本。
- 运行时兼容性检测、版本 gate、警告、拒绝或自动提升 fixture。
- 编辑、替换、克隆、验证、选择或自动管理任一 cc-switch 配置。
- 从 cc-switch 启动或停止记录器，或在记录数据路径中运行 cc-switch 自身代理。
- 单独的记录器认证方案，或替换上游凭据。
- 面向用户的对话文本捕获、对话重建、查看器、搜索、分析、回放、导出、仪表盘、Web UI，或语义 SSE/JSON 索引。
- 精确 header 行空白、传输成帧、交付 chunk 边界、时间忠实性、HTTP chunk-size 行、TLS record、TCP 分段和抓包。
- 任一 hop 上的 HTTP/2。
- VS Code webview、UI 和 extension-host IPC 自动化；验收止于扩展内置模型客户端入口。
- 在本次规格发布变更中实现记录器。代码、包脚手架和测试只能在用户审核本规格后开始。

## 补充说明

- 本规格综合了全部十张已解决设计票，不重新讨论其决策，也不在记录器之外增加第二套配置/配置管理产品。
- 已接受的 Node.js/流式 ADR 与本规格一致，不存在需要修改 ADR 的冲突。
- 目标技术栈 fixture 包含精确请求和响应 body，并带有目标技术栈的私密上下文。凭据值已经脱敏，但它仍必须是本地、非公开测试资产。
- 生产记录比 fixture 更敏感，因为忠实性明确包含凭据以及所有私密请求/响应内容。这是有意为之；保护和脱敏属于独立且不在范围内的工作。
- 最关键的审核点是测试接缝：一个组装后记录器边界，用于确定性字节/生命周期行为；再加一个真实技术栈兼容性边界，用于两个执行端入口。这样可以保持测试契约处于高层，同时区分字节真值与实时兼容性。
- 其他审核点包括精确产物 schema、首个合格会话准入规则、正常停止排空语义，以及刻意保持狭窄的第二 hop 允许差异列表。
- 发布本规格时未添加任何实现代码。
